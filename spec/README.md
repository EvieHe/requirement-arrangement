# Spec 目录约定

本目录用于存放 requirement-arrangement 项目的需求规格、技术方案和验收标准。每个独立需求使用一个子目录，避免把多个需求混在同一份文档中。

## 目录结构

```text
spec/
├── README.md
└── <requirement-slug>/
    ├── README.md
    ├── api.md            # 可选：接口与外部依赖
    ├── data-contract.md  # 可选：数据结构 / JSON / 流程变量
    └── tasks.md          # 可选：实施任务拆解
```

## 每个需求子目录的 README.md

每个需求必须有 `README.md`，并作为该需求的事实入口。建议按以下顺序组织：

1. 背景与目标
2. 范围 / 非范围
3. 用户使用方式
4. 数据来源
5. 页面与交互
6. 数据契约 / 流程变量
7. 状态与异常处理
8. 实现约束
9. 验收标准
10. 已知限制 / 待确认项

## 编写原则

- 文档描述“系统最终应该是什么”，不要记录聊天过程。
- 已确认事实和假设分开写；不确定项必须明确标注。
- 页面、Skill、SOP、后端接口如果存在契约关系，要写出字段和数据流，不只描述 UI。
- 真实接口未知时写“待确认”，禁止凭空创造 API。
- Mock 只能用于开发模式，不能作为生产数据源。
- 实现完成后如果代码行为与 spec 不一致，必须更新 spec 或修正实现，不能长期漂移。
- 同一个需求的重要设计决策尽量沉淀在该子目录下，不要散落在仓库根目录。
